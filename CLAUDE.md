# CLAUDE.md

- Do not end a report with an offer, a suggestion or a question about further work the user did not ask for, such as staging a file, committing, or making another change. Report what was done and what was verified, and stop there.
- Do not mention a physical device in a report, such as saying that something was or was not checked on one. State only what was verified.
- Do not use the expression "実機" in any text, including reports, comments, commit messages and pull request descriptions.
- Do not mention whether changes are committed or uncommitted in a report. Say only what was changed and what was verified.
- Do not append an `echo` that announces the end of a command or its result, such as `; echo finished`, `; echo done` or `&& echo identical`. A background task already reports its completion, and a foreground command returns when it ends.
- Do not open a pull request on a repository owned by an external team or account, such as the upstream of a fork, unless explicitly instructed to. Open pull requests only on repositories the user owns.
- Do not post a comment on a pull request, such as when closing one or after changing one, unless explicitly instructed to.
- Do not ask the user questions, including with the AskUserQuestion tool. Make a reasonable decision, proceed, and state the assumption made.
- Do not stop working to wait for the user's instructions, such as after an interrupted or rejected tool call. Treat the interruption as feedback, adjust the approach, and continue the task.
- Do not end a turn with a progress report, a status summary or a list of remaining steps while the task is unfinished, such as after a message that interrupts a tool call, a rejected tool call or a change of instructions. The user has not said to stop. Apply the feedback and keep calling tools until the whole task is done and verified, and report only then.
- Do not filter build output with `grep` (such as `grep -E "FAILED|error"`) or `tail`. Redirect the whole output of a build command to `build.log` in the scratchpad directory, overwriting the same file each time instead of numbering new ones, and inspect it with the Read tool. Apply the same to the output of any other command whose result is saved to a file, such as probes and device logs: do not create a separate file per run, such as `probe-tls1.log` and `probe-tls12.log`, or per variant, but overwrite one file.
- Do not send network requests to external domains, such as probing a server with `openssl s_client` or `curl`, without the user's approval. Test against a local server instead.
- Run build commands with verbose output from the first run, such as `flutter build linux -v` or `ninja -v`, so that a failure can be diagnosed from `build.log` without running the build a second time just to see the error.
- Run build and analysis commands (`flutter`, `cargo`, `cmake`, `ninja`) inside the development shell of the repository, with `nix develop`, instead of looking for tools on the host or in the Nix store.
- Do not copy packages out of the pub local store (`~/.pub-cache`) into the repository, and do not modify the files inside it. When a dependency needs a change, make it in the dependency's own repository, added as a submodule.
- Do not chain commands that serve different concerns into one Bash call with `&&`, `;` or a loop, such as an edit with `sed` followed by a build, or a `git checkout` followed by a build. Run each concern as its own call.
- Create a new crate with `cargo new`, and do not write a new `Cargo.toml` by hand from guesswork.
- Add a dependency with `cargo add`, and do not write a crate version into `Cargo.toml` from guesswork.
- Do not add a test on your own initiative. Add a regression test only for a problem the user has reported, and not for a change that nobody has reported a problem with.
